# 智能成人设备 BLE 控制器 — 通用业务协议规范

**版本**：v1.2  
**日期**：2026年6月12日  
**状态**：正式发布  
**协议类型**：设备无关通用业务协议（Common Business Protocol / Standard Intermediate Representation）

---

## 1. 协议定位与架构角色

本协议是**设备无关的通用业务协议**，用于在自然语言指令与底层硬件专用协议之间建立标准化中间层。

### 架构定位
- **上游**：自然语言解析器（NLP Parser）负责将用户口语/文本指令转换为本协议定义的符号字符串。
- **下游**：各设备的**协议转换/适配层（Device Protocol Adapter Layer）** 负责将通用符号翻译成该设备专用的 BLE 指令集或原生指令格式。
- **设计类比**：本协议相当于高级语言中的抽象接口或中间表示（IR）；运行时由具体设备的“转换器/适配器”负责翻译成目标硬件的机器指令。

### 设计目标
- 所有设备共享同一套解析逻辑和符号语义，降低 NLP 模块的维护与测试成本。
- 新增设备时，仅需开发对应的适配层，无需修改解析规则或符号定义。
- 功能集合固定为四类核心模块：伸缩（t）、震动（v）、吮吸（s）、加热（h）。
- 模式编号、强度值在通用协议中均为**逻辑抽象语义**，由适配层根据设备实际能力进行物理映射。

## 2. 术语与符号定义

### 2.1 功能模块（固定不变）
| 符号 | 模块名称 | 逻辑语义                     |
|------|----------|------------------------------|
| `t`  | 伸缩     | 伸缩/往复运动强度或模式      |
| `v`  | 震动     | 震动强度或模式               |
| `s`  | 吮吸     | 吸力/负压控制                |
| `h`  | 加热     | 加热/温度控制                |

### 2.2 操作符定义（逻辑抽象语义）
由设备协议适配层负责将以下逻辑操作符映射为具体设备的物理参数（PWM、档位、步进值、模式索引等）。

**伸缩 (t) 与 震动 (v) 共用操作符**：

| 操作符 | 逻辑语义         | 典型用户表达示例             |
|--------|------------------|------------------------------|
| `+`    | 加速/增强/加快   | 快一点、强一点、猛一点、加速 |
| `-`    | 减速/减弱/放慢   | 慢一点、弱一点、轻一点       |
| `s`    | 停止/关闭        | 停、停止、关掉、别动、关闭   |
| `m`    | 全速/最大强度    | 全速、最大、最猛、100%       |
| `o`    | 开启/启动        | 开始、启动、动起来、打开     |
| `f`    | 关闭             | 关掉、关闭、别开了           |
| `c`    | 继续/恢复        | 继续、接着来、恢复           |
| `0-100`| 设定逻辑百分比强度 | 调到50、设成30%、强度50      |

**吮吸 (s) 专用操作符**：

| 操作符 | 逻辑语义     | 典型用户表达示例             |
|--------|--------------|------------------------------|
| `u`    | 开启吸力/吸紧 | 吸一下、吮吸、吸住、酸吸、船吸 |
| `d`    | 释放/放气    | 吹、放气、吐气、排气、松开   |
| `s`    | 停止吸力     | 停吸、别吸、松开、关闭吮吸   |
| `o`    | 开启吮吸     | 开吸、打开吮吸、启动吮吸     |
| `f`    | 关闭吮吸     | 关闭吮吸、别吸了             |
| `c`    | 继续/恢复吮吸 | 继续吸、接着吸               |

**加热 (h) 专用操作符**：

| 操作符 | 逻辑语义 | 典型用户表达示例                  |
|--------|----------|-----------------------------------|
| `o`    | 开启加热 | 有点冰、好凉、冷、冻死、凉飕飕、太冷 |
| `f`    | 关闭加热 | 太热、热死、好热、烫死、热爆、太烫   |

## 3. 输出格式规范（强制性）

解析器必须严格遵守以下格式，**仅输出单行内容**，不得包含任何解释、文字、标点、换行或多余空格。

### 3.1 普通调整格式
```
符号1|符号2|符号3|...
```
示例：`t:20|v:+|s:u|h:o`

### 3.2 模式切换格式
```
CM->t:数字|v:数字|s:数字
```
- 前缀固定为 `CM->`。
- 仅包含明确指定了模式的模块；未指定模式的模块按普通操作符处理，但仍使用 `CM->` 前缀。
- 模式号范围为 `1-100`，超出视为无效。
- 加热模块（`h`）**不支持模式**，任何 h 模式尝试均被忽略。
- 示例：`CM->t:2|v:+`

### 3.3 特殊输出
- **无法解析**：`e:无法解析`
- **无有效调整**：空字符串（长度为 0）

**符号分隔符**：仅使用单个 `|`，前后均无空格。所有字母均为小写。

## 4. 解析规则（严格优先级顺序）

解析器执行时必须按以下顺序依次判断与应用规则。规则负责生成**通用业务协议符号**，与具体设备无关。

### 优先级 1：模式切换检测（最高优先级）
**触发条件**（任一满足即触发）：
- 包含关键词：“模式”、“切模式”、“切换模式”、“用模式”、“第几个模式”等。
- 明确使用“伸缩模式X”、“震动模式X”、“吮吸模式X”表述（X 为数字或中文数字）。

**处理逻辑**：
- 提取模式编号（从 1 开始）：“模式一”→`1`，“第三个模式”→`3`，“模式 2”→`2`。
- 支持中文数字自动转换。
- 混合指令：模式部分转换为数字，其余部分按普通操作符处理，仍输出 `CM->` 前缀。
- 示例：`伸缩模式2 震动快一点` → `CM->t:2|v:+`

### 优先级 2：全停指令
检测到全局停止意图（如“别动了”、“全停”、“全部关闭”）时，强制输出：
```
t:s|v:s|s:s|h:f
```

### 优先级 3：全局速率与模糊调整
- “都快”、“全速”、“都猛一点”等同时影响 t 与 v：
    - 普通增强：`t:+|v:+`
    - 全速：`t:m|v:m`
- 未指定具体模块的模糊指令（如“快一点”）默认同时作用于 t 和 v：`t:+|v:+`

### 优先级 4：负面反馈优先处理（指定功能优先）
负面反馈词优先于普通正向调整，且仅影响明确提及的功能模块。

**速率类 (t / v)**：
- 太慢/太弱/慢死/弱爆 → `+`（增强）
- 太快/太强/快死/强爆 → `-`（减弱）

**加热类 (h)**：
- 太热/热死/好热/烫死/热爆/太烫 → `f`（关闭加热）
- 太冷/冷死/冻死/冰凉/凉飕飕 → `o`（开启加热）

**指定功能优先规则**：
- 用户明确提及模块（如“真动太慢了”）时，仅输出该模块符号。
- 未明确指定模块时，按默认对应符号处理（加热单独判断）。

### 优先级 5：ASR 容错与同音字推断
基于发音相似性自动映射常见错误：
- 酸吸/船吸 → `s:u`
- 真动 → `v`（震动）
- 深缩 → `t`（伸缩）
- 其他音似错误按语义最近匹配处理。

### 通用约束
- **最小输出原则**：仅输出指令中明确或隐含提及的功能模块符号，未提及的模块不输出。
- **无法解析回退**：无任何有效功能匹配或意图无法识别时，输出 `e:无法解析`。
- **数字强度**：0-100 范围有效，超出按边界处理或视为无效。

| 用户指令     | 通用协议输出            | 应用规则说明             |
|--------------|-------------------------|--------------------------|
| 震动快一点   | `v:+`                   | 仅震动模块增强           |

| 别动了       | `t:s|v:s|s:s|h:f`       | 全停指令                 |
| 太热了       | `h:f`                   | 加热关闭（热反馈）       |
| 热死了       | `h:f`                   | 加热关闭（热反馈）       |
| 太冷了       | `h:o`                   | 加热开启（冷反馈）       |
| 烫死了       | `h:f`                   | 加热关闭（热反馈）       |

|-------------------------------|-------------------------|----------------------------------|

| 伸缩模式1 震动模式3 吮吸模式2 | `CM->t:1|v:3|s:2`       | 多模块模式同时切换               |

| 用户指令     | 通用协议输出   | 应用规则说明                  |

## 6. 设备协议转换/适配层职责

设备协议适配层是本架构的关键组件，负责将通用业务协议符号转换为设备专用指令。

### 主要职责
1. **符号到设备指令的映射**  
   将 `t:2`、`v:+`、`CM->t:3` 等逻辑符号转换为该设备 BLE 协议的具体数据包、命令码、参数值。

2. **逻辑值到物理值的映射**  
   将 `+`、`-`、`m`、`0-100` 等逻辑意图映射为设备实际支持的档位、PWM 占空比、步进速度或模式索引。不同设备最大档位数可能不同，适配层需进行归一化或裁剪。

3. **功能裁剪与降级处理**  
   若设备不支持某功能（如无加热），适配层应忽略对应符号或按产品策略返回错误码/降级处理。

4. **状态同步与补偿**  
   可维护当前设备状态，并在必要时对通用协议输出进行补偿（如设备不支持“模式”概念时，将 `CM->t:2` 降级为强度设置）。

5. **错误处理与日志记录**  
   记录映射失败、设备不支持的功能等信息，便于上层决策与问题排查。

### 实现建议
- 每类设备实现一个独立的 `DeviceAdapter`（推荐采用策略模式或工厂模式）。
- 适配层输入：通用协议符号字符串 + 设备类型/型号标识。
- 适配层输出：设备专用的 BLE 写特征值数据或指令对象列表。
- 建议为每个适配层编写独立的单元测试与集成测试用例。

## 7. 实施与验证建议

1. **推荐分层架构**：
    - NLP Parser（生成通用协议符号）
    - Device Protocol Adapter（各设备独立实现）
    - BLE 通信层 / 硬件抽象层

2. **测试策略**：
    - Parser 层：仅验证是否正确生成通用符号（以本协议示例为 truth source）。
    - Adapter 层：针对具体设备进行端到端指令正确性测试。
    - 集成测试：覆盖 Parser 与多个 Adapter 的组合场景。

3. **扩展性保障**：
    - 新增设备 → 仅需新增 Adapter 实现，无需修改 Parser 或本协议。
    - 新增功能模块 → 需同步修订本协议版本，并更新所有现有 Adapter。

4. **版本与兼容性管理**：
    - 本通用协议升级时，需评估对现有 Adapter 的兼容性，建议采用向后兼容策略或版本号协商机制。
